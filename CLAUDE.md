# FCP Connect

Job-site photo and video app for a commercial contractor: projects, geotagged
media, maps, comments, checklists, divisions and role-based access. Started in
Lovable; since 2026-10-16 it runs on its own Supabase project (`afhlutsdgvsmvitzxhvr`,
org "FCP Services", East US Ohio) and a Cloudflare Worker (`fcp-connect`), live at
https://fcp-connect.fcpservices.workers.dev.

## Lovable (front-end editing only)

The Lovable project syncs two ways with the `lovable` branch, never with `main`.

- Lovable is for screens, layout and copy. Database, auth and access-rule changes
  go through the factory as migrations in `supabase/migrations/`.
- Lovable's preview runs against the production Supabase project: anything done in
  it creates real data. Never use Lovable's Publish button; the live site is only
  deployed from `main`.
- "Merge lovable": review `git diff main...origin/lovable` first and stop if it
  touches `.env`, `src/integrations/supabase/`, `wrangler.jsonc`,
  `supabase/config.toml`, `vite.config.ts`, adds `drizzle/` or a migration, or
  changes dependencies. Otherwise merge into `main` and run Validation; the
  human pushes `main` to deploy.
- "Update lovable": merge `main` into `lovable` and push `lovable` (this deploys
  nothing), so Lovable sees the latest code.

## Stack

- TanStack Start (SSR) + TanStack Router file routes, React 19, TypeScript, Vite 7
- Tailwind CSS 4, shadcn/ui on Radix (`src/components/ui/`), lucide-react icons
- Supabase: auth, Postgres, storage (private `job-photos` and `safety-documents` buckets). Client in
  `src/integrations/supabase/`; schema in `supabase/migrations/` (the only migration folder)
- Server functions in `src/lib/*.functions.ts`; Cloudflare Workers deploy (`wrangler.jsonc`)
- Leaflet maps, exifr (EXIF/GPS), jsPDF / html2canvas / jszip for exports

## Environment

- Windows 11; Claude Code runs shell commands in Git Bash. Node 24, npm.
- Use `npm` (`package-lock.json`). The Supabase CLI is a dev dependency (`npx supabase`).
- Python: use `python`, not `python3` (the Microsoft Store alias).
- `.env` is committed and holds only the Supabase URL and publishable keys. It
  points at the **production** database.

## Dev server

```bash
npm run dev -- --port <port> --strictPort
```

Open `http://localhost:<port>/`. Most pages need a signed-in user; without test
credentials, check logged-out pages (`/login`, `/reset-password`, `/share/<token>`)
and review the rest from code.

### agent-browser on this machine

The first `agent-browser` call of a session starts a background daemon that
keeps the command's output pipe open, so piping it (`| tail`, `| head`) hangs
the shell. Redirect output to a file and read the file instead:

```bash
agent-browser --session <s> open http://localhost:<port>/login > "$TEMP/ab-<s>.txt" 2>&1; cat "$TEMP/ab-<s>.txt"
```

Run the dev server in the background (not piped) and stop it when done.

## Validation

Run all four; each must pass before a build is READY.

- Type-check: `npx tsc --noEmit`
- Lint: `npx eslint <changed files>`. Lovable does not run Prettier, so many
  existing files carry pre-existing `prettier/prettier` errors. Only errors on
  lines the change adds or edits count; never reformat lines you did not change
  (no `--fix` or `prettier --write` on whole existing files).
- Build: `npm run build`
- Tests: `npm test` (Vitest, `vitest run`). Test files live next to the code as
  `src/**/*.test.ts`; the suite must pass before a build is READY.

## Conventions

- `/` is the Home launcher (tiles for Projects, Safety, Messages and, with the National Paint permission, National Paint) and the Projects list is at
  `/projects`. A new top-level suite gets a launcher tile and a header nav link.
- Routes are files in `src/routes/` (`project.$projectId.tsx` = `/project/:projectId`).
  `src/routeTree.gen.ts` is generated by the router plugin; never hand-edit it.
  Builds and the dev server rewrite it in a different import order; if the
  feature adds no route, revert it (`git checkout -- src/routeTree.gen.ts`)
  instead of committing the reorder.
- Do not add plugins to `vite.config.ts`; `@lovable.dev/vite-tanstack-config`
  already includes them (see the comment in that file).
- Use the existing shadcn components in `src/components/ui/` and Tailwind
  classes; feature components live in `src/components/`, shared logic in `src/lib/`.
- Use the `@/` import alias. Prettier: double quotes, semicolons, width 100,
  trailing commas.
- Access rules (roles, divisions, collaborators, view-as/proxy) are enforced in
  Supabase RLS and `src/lib/*.functions.ts`; UI checks are not enough on their own.
- View As (admin proxy) is read-only. Writes still run on the admin's own session, so
  every create/edit/delete/upload control checks `readOnly` from `useProxy()`
  (`src/lib/proxy-context.tsx`) and is hidden or disabled while it is true. New write
  controls must do the same. Read-only is also enforced in the database: `adminStartProxy`
  records a `proxy_sessions` row (expires after 2 hours, closed by `adminEndProxy`) and
  restrictive INSERT/UPDATE/DELETE policies refuse writes from an admin with an active
  session. Any new table with write policies must get matching restrictive
  INSERT/UPDATE/DELETE policies using `private.has_active_proxy(auth.uid())` in its migration.
- `audit_log` rows are written only by server functions through the service role
  (`supabaseAdmin`). There is no client-side insert policy, so new audit entries must be
  written from `src/lib/*.functions.ts`, never from the browser.
- The public share RPC `get_shared_job` returns only an explicit field list and excludes archived
  photos, and new `share_links` expire after 30 days by default. Any new field the share page
  needs must be added to `get_shared_job` in a new migration.
- `worker_type`, `subcontractor_name` and `is_disabled` on `profiles` are admin-only. They are
  enforced by the `profiles_admin_fields_guard` trigger and set only from
  `src/lib/admin.functions.ts` through the service role.
- Safety document writes go through `src/lib/safety.functions.ts` using the caller's RLS client,
  files are served only by signed URLs, and subcontractors see only `shareable_with_subs`
  documents (enforced in RLS and mirrored for View As by `visibleToViewer`).
- `safety_acknowledgements` rows are inserted only by the user themselves (via
  `acknowledgeSafetyDocument`) and are never changed or deleted; `manage_safety` reads all of them.
  Acknowledgement is per `safety_documents.revision`, which the `safety_documents_set_revision`
  trigger bumps when the file is replaced.
- JHA writes go through `src/lib/jha.functions.ts`. `jha_records` are readable only by the project
  owner (`owner_id`), collaborators and `manage_safety`. A JHA is completed once per project and
  redone only after a "Request new JHA", enforced by the `jha_record_guard` trigger; completed
  records cannot be changed.
- Toolbox talk writes go through `src/lib/toolbox-talks.functions.ts`. `toolbox_talks` are readable
  only by the project team (owner and collaborators) and `manage_safety`, reusing
  `private.can_access_jha`; topics are managed by `manage_safety`. A talk is completed once with
  attendee signatures and then cannot be changed, enforced by the `toolbox_talk_guard` trigger.
- Messages are in-app only (no email or push). Recipients are resolved server-side by
  `resolveAudience` in `src/lib/messages.ts`; sending goes only through `sendMessage` in
  `src/lib/messages.functions.ts`, which writes the `message_sent` audit entry.
  Read receipts are set only by `markMessageRead` in `src/lib/messages.functions.ts`, under the
  caller's RLS; a trigger allows only `read_at` to change, and only once. Under View As, message
  reads pass `viewAsUserId` and go through `resolveReader`, which requires an admin with an active
  `proxy_sessions` row for that user. No receipt is recorded: the client skips `markMessageRead`
  and the restrictive policy refuses it.
- National Paint is gated by the `manage_national_paint` permission (`app_roles.can_manage_national_paint`):
  one level covering view, edit and finance, off by default, always on for admins. Its eight `np_*`
  tables (`np_pms`, `np_contractors`, `np_crews`, `np_crew_members`, `np_projects`,
  `np_budget_targets`, `np_cmic_jobs`, `np_cmic_cost_lines`) use permission RLS plus the restrictive View As policies. National Paint
  writes go through `src/lib/national-paint.functions.ts`. The workbook import is admin-only: the
  .xlsm is parsed in the browser (`src/lib/national-paint-import.ts`), applied atomically by the
  `np_import_workbook` function and audited as `national_paint_imported`. People and crews
  (PMs, contractors, crews, crew members) writes go through `src/lib/national-paint.functions.ts`
  under the caller's RLS; deleting a PM, contractor or crew in use by projects (or a contractor
  with crews) is refused, and the audit actions are `national_paint_<entity>_created|updated|deleted`
  (entity `pm`, `contractor`, `crew` or `crew_member`). Project writes (create, update, delete and
  the quick status change) also go through `src/lib/national-paint.functions.ts` under the caller's
  RLS, audited as `national_paint_project_created|updated|deleted|status_changed`. A project's crew
  must belong to its contractor (checked on the server). Pace is computed in the browser by
  `computePace` in `src/lib/national-paint-projects.ts` (the workbook formula) and is not stored;
  Progress is entered by hand. The Project Timeline (`/national-paint/timeline`) is read-only; bars
  follow the workbook rule in `src/lib/national-paint-timeline.ts` (140 days from a reference date,
  Start and End inclusive, no bar without a Start, open-ended without an End) and dates are edited
  in the project form. The Crew Capacity page (`/national-paint/capacity`) is read-only; its rules
  live in `src/lib/national-paint-capacity.ts`: 120 days from a reference date; busy = Scheduled
  or In Progress; a project counts only between both dates, inclusive; projects match by
  `crew_id`; inactive crews are Unavailable at 0%; % Busy and overlap days cover
  Reference..Through; an overlap is a day with two or more busy projects. The Revenue
  (`/national-paint/revenue`) and Dashboard (`/national-paint/dashboard`) pages are read-only except
  the monthly targets; their rules live in `src/lib/national-paint-revenue.ts`: revenue is split over
  calendar days from Est Start to Est End inclusive, only Verbal Award, Upcoming, Scheduled, In
  Progress and Completed count, Exclude Revenue or a missing date or revenue is 0, and Actual is
  Reported where entered, else Scheduled. `np_budget_targets.reported_revenue` (NULL = not reported)
  is saved only by `saveNpMonthlyTargets` under the caller's RLS and audited as
  `national_paint_budget_saved`; a workbook re-import resets the year's reported values to blank.
  CMiC uploads (`/national-paint/cmic`) need `manage_national_paint`. The two CMiC exports are parsed
  in the browser (`src/lib/national-paint-cmic.ts`) and replace one report's rows atomically
  through `np_replace_cmic`; they never touch `np_projects`, and are audited as
  `national_paint_cmic_uploaded` with counts only. Matching rules live in
  `src/lib/national-paint-cmic-match.ts` (the workbook "CMiC Job #" and "JobCost Match" formulas,
  plus the ranking). Matches are saved only by `setNpProjectCmicJob` (audited as
  `national_paint_cmic_match_set`). A workbook re-import still replaces `cmic_job_number` from the
  workbook.
  Real National Paint data,
  workbooks and CMiC exports must never be committed; tests use made-up rows.
- New pure helpers in `src/lib/` get a colocated `*.test.ts`. Tests must not hit the
  network or Supabase: stub `fetch` and modules with `vi` (`vi.stubGlobal`, `vi.mock`).

## Production safety (all agents)

- **A push to `main` goes live.** GitHub Actions (`.github/workflows/deploy.yml`)
  type-checks, tests and builds, then applies pending migrations to the production
  database and deploys the Worker. Pushing is the human's approval step.
- Never run migrations, `supabase db push`, `supabase db query`, or SQL against the
  database. A schema change is written as a new file
  `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql` (later than every existing one);
  it is applied by the pipeline when a human pushes.
- Never deploy (`wrangler deploy`), never `git push`, never edit `.env` or
  `wrangler.jsonc` vars, never set Worker or GitHub secrets.
- The dev server talks to production data. In the browser, look and navigate
  only: do not submit forms, upload media, comment, or click anything that
  creates, edits or deletes data.

## Factory merge policy

The mode is in `factory/mode` (`quick` or `slow`; missing means `slow`); set it
with `/factory quick` and `/factory slow`.

- **slow**: every job escalates. The approver always writes `ESCALATE` on the first
  line and starts `## Why` with `Recommendation: APPROVE` or `Recommendation: ESCALATE`.
  The human merges with `/factory approve <job-id>` after reading `decision.md`.
- **quick**: the approver writes `APPROVE` unless it finds a real problem (unmet
  criterion, review issue, conflict, a product decision hidden in an assumption, or a
  concrete security or migration flaw). The orchestrator merges locally and `/factory
  next` continues through the backlog until a job escalates. Every `decision.md` lists
  its sensitive areas (migrations, access rules, dependencies, config).
- In both modes the human's push to `main` is the approval step: the factory never
  pushes, so nothing deploys until the human has reviewed and pushed.
